> 状态：PG0～PG5、编辑区铺满修复、自动/手动验收和独立本地提交均已完成
> 关联评估：[assessment.md](./assessment.md)
> 创建日期：2026-07-27
> 方向确认日期：2026-07-27
> 已选择：L2 页面重设计 + 所有等级必须完成的可靠性修复；不纳入 L3-A
> 已确认原型：`design-preview/notes-l2.html`、`design-preview/notes-report-integrated.html`

## 1. 页面范围

本次门禁覆盖工时内容页面的周次导航、工作日与周末显示、每日标题和正文编辑、800ms 自动保存、保存与加载状态、代码周报参考、亮暗主题、900 × 600 最小窗口以及 Vue 迁移后的请求和组件生命周期。

不包含：

- 不再建设代码周报独立页面；其有效查询、分组、复制、导出和写入能力已经吸收到工时内容页，GitLab 配置继续由系统设置维护。
- 完整离线优先体系、跨设备同步或历史版本管理。
- 侧边栏、Vue Router 和应用壳迁移。
- 未经 PG3 单独确认的数据库表、Sidecar 协议或报告生成流程变更。

## 2. 所有等级都必须修复的可靠性问题

以下内容不是可选视觉优化。无论 PG3 选择 L0、L1、L2 或 L3，都必须作为 Vue 迁移正确性门槛：

1. 切换周次、切换页面或组件卸载前，必须 flush 尚未触发的 800ms 防抖保存；保存失败时保留可恢复草稿，不能静默丢失输入。
2. 404“当天没有记录”必须与超时、Sidecar 断开、500 和解析失败分开处理。
3. 保存状态必须属于具体日期，不能继续使用会被多日请求互相覆盖的全局“已保存”文本。
4. 接口失败后不能继续显示陈旧的成功状态；必须提供明确错误和重试路径。
5. 快速连续切周必须具备请求所有权、取消或最后一次请求生效规则，旧请求不能覆盖新周数据。
6. 已有 SQLite `notes` 数据、本地日期口径、字段和周末偏好必须兼容，不重置、不迁移或删除用户数据。
7. Git 活动工作区展开后允许占用右侧空间并压缩编辑区，但 900 × 600 下必须重排周列表，保证编辑器、活动列表和底部动作都可操作，页面不得出现横向滚动、重叠或裁切。
8. 旧页面的全局函数、字符串 `innerHTML`、内联事件和 CSS 覆盖链不得复制进 Vue SFC。

## 4. 公共组件与页面私有组件边界

### 4.1 直接复用的公共组件

- `PageFrame`：使用 `workspace` 形态承载周编辑工作区。
- `PageTop`、`PageToolbar`：统一标题、周次导航、周末开关和顶部操作。
- `BaseButton`、`BaseIconButton`：上一周、本周、下一周、重试和打开参考。
- `BaseInput`、`BaseTextarea`：标题和正文编辑、label、错误、焦点和禁用状态。
- `BaseSwitch`：周末显示开关。
- `BaseCard`、`StatusIndicator`：每日编辑表面和保存状态。
- `LoadingState`、`EmptyState`、`ErrorState`：加载、无数据和错误反馈。

如现有输入组件不能满足自动增长需求，优先通过已登记 prop/slot 扩展公共组件；只有两个以上页面存在稳定共性时才升级为新公共能力。

### 4.2 工时页面私有组件

```text
frontend/src/views/notes/
├── NotesView.vue
├── components/
│   ├── WeekNavigator.vue
│   ├── DailyWorkNote.vue
│   └── ReportReferencePanel.vue
└── composables/
    └── useWeeklyNotes.ts

frontend/src/services/modules/notes-service.ts
```

- `WeekNavigator.vue` 只负责周范围、上一周、本周、下一周和周末开关。
- `DailyWorkNote.vue` 只负责单日字段、单日保存状态和重试事件。
- `ReportReferencePanel.vue` 只消费类型化参考数据，不读取其他页面 DOM。
- `useWeeklyNotes.ts` 负责日期派生、请求所有权、防抖队列、flush、草稿和页面状态。
- `notes-service.ts` 负责 API DTO、404/错误归一化和保存请求，不包含视觉状态。

## 5. L0～L3 方案

### L0：可靠迁移

**内容**

- 基本保留现有五日/七日纵向卡片布局和信息结构。
- 完成 Vue SFC、service、composable、公共组件接入和旧 CSS 清理。
- 完成第 2 节全部可靠性修复、错误状态和 900 × 600 响应式修复。
- 代码周报引用改为类型化 adapter，不允许继续抓取 DOM；L0 只提供稳定的 Git 活动空状态和 service 边界，完整右侧工作区属于已确认的 L2。

**优点**：范围最小，最快完成架构迁移。

**不足**：页面仍会保留较强的“大面积文本编辑框”观感，五日/七日空间利用只做必要修复。

**HTML 原型**：不需要。

**估算**：约 2～3 个净工程日，不含用户手动 E2E。

### L1：一致性与轻量体验优化

**内容**

- 包含 L0 全部内容。
- 使用统一 Page、Toolbar、Button、Textarea、Switch、Card 和 Feedback 组件。
- 优化间距、字体、日期层级、当前日表达和每日保存反馈。
- 增加“回到本周/今天”、参考空状态跳转和最小窗口参考抽屉。
- 不改变“一天一张纵向编辑卡”的主要布局。

**优点**：无需重画页面即可明显改善一致性、文字压力和操作反馈。

**不足**：空间结构仍接近旧页面，七日模式和沉浸式编辑体验提升有限。

**HTML 原型**：通常不需要，可直接以公共组件预览和实现验收。

**估算**：约 3～4 个净工程日，不含用户手动 E2E。

### L2：周工作空间重设计

**内容**

- 包含 L1 和全部可靠性修复。
- 重新设计周工作空间、周次导航、每日编辑卡、五日/七日高度策略和参考周报打开方式。
- 重点减少同屏大段文字边框的视觉疲劳，同时保证默认窗口铺满和小窗口可读。
- 明确亮色、暗色以及 1665 × 1184、900 × 600 的最终布局。
- 不改变数据库结构，不引入复杂任务语义。

**优点**：在本次 Vue 迁移中一次解决架构、空间利用和页面观感问题，避免迁移完成后再次重做布局。

**风险**：必须先冻结原型，避免编码阶段持续调整信息结构。

**HTML 原型**：需要；PG3 确认 L2 后先制作亮暗主题可交互 HTML 原型，用户确认最终原型后才进入 PG4。

**估算**：原型约 1～2 个净设计日；实现与验证约 4～6 个净工程日。

### L3：数据能力与恢复体系

**内容**

- 包含 L2。
- 可选增加按周批量读取 API、持久化草稿恢复、空记录清理策略和稳定的跨页周报共享数据模型。
- 对周报日期范围进行校验，确保查看历史周时不会引用错误周期的报告。
- Sidecar、数据库或跨页状态契约按子阶段独立设计、测试和提交。

**优点**：可靠性和跨页数据模型最完整，减少 7 次读取和重载后的草稿风险。

**风险**：会扩大 Sidecar 或本地持久化范围；必须拆成独立子阶段评审，不能在页面迁移中顺带加入。

**HTML 原型**：需要；同时需要 API、持久化和跨页契约的范围确认。

**估算**：在 L2 之外增加约 3～6 个净工程日，取决于最终 API 和恢复范围。

## 6. 推荐方案

推荐 PG3 选择：**L2 + 所有等级必须完成的可靠性修复**。

理由：

1. 旧页面主要体验问题不仅是样式，而是五日/七日空间策略和大面积同质文本框带来的视觉疲劳，L0/L1 只能缓解，不能重建工作空间。
2. 用户此前已明确希望在页面 Vue 迁移时同步研究并优化页面，L2 与该执行方式一致。
3. L2 不要求修改数据库或 Sidecar，可以把视觉和架构放在一个受控页面提交中完成。
4. 完整 L3 暂不推荐现在执行。现有 `/api/report` 契约已经足够支持 L2 Git 活动工作区，持久草稿、批量 API 或历史版本应按真实需求单独立项。

如特别重视应用意外退出或重载后的草稿恢复，可在推荐方案上单独增加 **L3-A：持久草稿恢复**；这需要 PG3 额外确认存储位置、保留周期和清理规则。
