# DevTools 全页面顶部区域审计

> 审计日期：2026-07-21  
> 本地地址：`http://127.0.0.1:1420`  
> 审计范围：14 个侧边栏页面的顶部区域  
> 采集尺寸：1665 × 1184、900 × 600  
> 主题：亮色、暗色

## 1. 审计目标

本次审计用于回答两个问题：

1. 当前 14 个页面顶部区域分别采用了什么结构，为什么视觉和交互不一致。
2. 如何建立一套能够覆盖现有页面的公共 Vue 顶部组件，同时避免形成参数过多、难以维护的“万能 Header”。

本次只进行现状取证和组件方案设计，不修改正式页面代码。

## 2. 视觉证据

截图、contact sheet 和尺寸测量均属于本地审计产物，不进入 Git 仓库。需要复核时，按照当前测试基线重新启动开发服务并采集对应窗口尺寸；输出目录已由项目 `.gitignore` 排除。

本报告只保留可长期维护的结构结论和组件规格，避免把一次性截图变成仓库负担。

## 3. 总体结论

当前页面虽然普遍使用了 `.page-title`、`.page-subtitle` 和 `.page-toolbar`，但并没有真正共享同一个组件或唯一布局规则。

目前至少存在五套顶部结构：

1. `.page-fixed-header + .page-scroll-body`
2. `.page-header-bar + .page-toolbar`
3. `.notes-fixed-header`
4. 标题嵌套在页面业务容器中的结构，例如 `report-app`
5. 首页沉浸式 Hero，无普通页面顶部

CSS 中同一标题和顶部选择器同时被 `layout.css`、`components.css`、`overrides.css` 和页面 CSS 多次定义。部分规则还通过页面 ID 和 `!important` 再次覆盖，所以“类名相同”并没有带来视觉一致性。

最终不建议只建立一个 `PageHeader.vue` 并加入大量布尔属性。更稳定的方案是建立一个公共顶部组合体系：

```text
PageFrame
├── PageTop
│   ├── PageHeader
│   │   ├── AppIcon
│   │   ├── Title + Description
│   │   └── PageActions
│   ├── PageSubnav       可选
│   └── PageToolbar      可选
└── PageBody
```

`PageFrame` 负责固定顶部和独立滚动正文；`PageTop` 负责统一背景、间距和分隔；其余组件通过组合覆盖不同页面，而不是让一个组件理解所有业务。

## 4. 逐页审计

| ---: | --- | --- | --- | --- | --- |
| 1 | 应用首页 | 沉浸式 Hero | 良好，作为例外 | 不属于普通工具页，不应强行套统一标题 | `PageFrame variant="immersive"`，不渲染 `PageTop` |
| 2 | 本地运行 | 标题 + 主操作 + 搜索筛选工具栏 | 需要优化 | 默认 107px；最小窗口工具栏换行后达到 149px；按钮与筛选同层较拥挤 | `PageTop + PageHeader + PageToolbar` |
| 3 | 部署面板 | 标题 + 主操作 + 子导航，搜索筛选位于子页 | 需要优化 | Page 级导航和子页工具栏分属两套容器，视觉上像一个区域，代码上并不统一 | `PageTop + PageHeader + PageSubnav + route toolbar` |
| 4 | 文件传输 | 标题 + 刷新 + 会话连接栏 | 需要优化 | 副标题很长；会话选择、连接和状态挤在一行；窄窗口缺少优先级 | `PageTop + PageHeader + PageToolbar` |
| 5 | 快捷命令 | 标题 + 添加 + sudo/保存工具栏 | 需要优化 | 未使用固定顶部骨架；工具栏内容偏右，宽窗口信息联系较弱 | `PageTop + PageHeader + PageToolbar` |
| 6 | 待办事项 | 标题 + 新建 + 单一清理工具栏 | 需要优化 | 第二行只有一个低频操作，制造空白；顶部与正文未使用统一固定骨架 | 将“清除已完成”放入次级操作或更多菜单 |

| 9 | 个人笔记 | 简单标题 + 工作区内双栏工具条 | 基本合理 | 页面标题可统一；搜索、新建和编辑器工具属于工作区，不应塞入全局顶部 | `PageTop + PageHeader`，保留私有 `NotebookToolbar` |

| 11 | 纯净检测 | 标题 + 查询工具栏 | 接近目标 | 结构清楚，但仍由全局 CSS 和页面 CSS共同控制 | `PageTop + PageHeader + PageToolbar` |
| 12 | 2FA 验证码 | 标题 + 3 个操作 + 搜索筛选状态栏 | 风险较高 | 操作区宽 301px；最小窗口接近极限；导入、导出、添加优先级未区分 | 主操作保留，导入导出进入 `PageOverflowMenu` |

## 5. 跨页面主要问题

### 5.1 结构不一致

- 只有本地运行、部署、文件传输、2FA 和用量统计使用 `.page-fixed-header`。
- 工时内容自己实现 `notes-fixed-header`。
- 快捷命令、待办、纯净检测等使用普通标题与工具栏，但顶部随整页结构变化。
- 代码周报的标题嵌入业务布局，无法作为独立公共区域管理。

结果是固定行为、正文滚动起点和顶部边界无法统一。

### 5.2 样式来源冲突

同一 `.page-title` 至少出现以下相互覆盖的方向：

- 初始字号 22px。
- `.page-header-bar .page-title` 调整为 18px。
- 后续共享头部规则调整到 20px。
- 视觉统一规则再次调整到 17px。
- 页面 ID 选择器和 `!important` 继续覆盖。

顶部样式已经形成“后写规则压前写规则”的优先级竞争。这也是公共组件必须同时删除旧选择器，而不能只增加一个 Vue 包装层的原因。

### 5.3 高度和正文起点不一致

默认窗口下主要出现：

- 简单标题：约 48～50px。
- 标题 + 工具栏：约 107px。
- 工时内容自定义顶部：122px。

900 × 600 下：

- 本地运行顶部：149px。
- 用量统计顶部：119px。
- 其他两行顶部：约 107～122px。

允许工具栏自然增高是合理的，但必须限制为可预测的 1～2 行，不能由各页任意换行。

### 5.4 操作优先级不清楚

- 页面右上角同时出现 3～4 个同权重操作。
- 低频操作长期占据标题行，导致标题和说明被压缩。
- 单一低频操作又可能独占第二行，例如“清除已完成”。

建议标题行最多保留一个主要操作和一个更多菜单；高频上下文操作才进入 Toolbar。

### 5.5 图标语言不统一

侧边栏使用线性 SVG，页面标题大量使用不同平台渲染效果的 Emoji。Emoji 的尺寸、基线、色彩和暗色主题表现无法稳定控制。

建议公共 PageHeader 使用统一的 `AppIcon` 和同一套 SVG 图标源，Emoji 只保留在内容表达中，不再作为结构性页面图标。

## 6. 可访问性风险

以下结论来自截图与 DOM 结构，只代表风险，不等同于完整 WCAG 验证：

- 多数页面标题使用 `div.page-title`，而不是页面唯一的 `h1`。
- 多组筛选和子导航看起来像 Tab，但未统一证明具有 `tablist/tab` 语义和键盘行为。
- 多个图标按钮只靠图形表达，需确认 accessible name、Tooltip 和最小点击区域。
- 浅色副标题和禁用态文字对比度偏低，需要进行真实颜色对比度测量。
- Toolbar 换行后需要维持可理解的键盘顺序和焦点顺序。

## 7. 推荐优先级

### P0：组件基础

1. 建立 `PageFrame / PageTop / PageHeader / PageActions / PageSubnav / PageToolbar / PageBody`。
2. 建立统一页面顶部 Token 和亮暗主题映射。
3. 标题使用页面唯一 `h1`，说明使用关联描述。
4. 用 `AppIcon` 替换结构性 Emoji。

### P1：高密度顶部

优先验证本地运行、部署面板、2FA 和用量统计。这四页覆盖主操作、多个次级操作、子导航、搜索、筛选、状态以及窄窗口折叠，是组件兼容性的压力测试。

### P2：普通页面迁移

将系统设置、个人笔记、代码周报等简单页迁入同一骨架，再处理工时内容、快捷命令和待办的业务工具栏归属。

## 8. 审计限制

- 浏览器模式可以确认布局、主题和 DOM，但不能证明 Tauri WebView 中的拖拽区域、惯性滚动和系统级功能完全一致。
- 截图不能验证完整键盘流程、屏幕阅读器名称和所有颜色对比度。
- 当前审计没有改变功能位置；“是否把某个按钮移入更多菜单”仍需在对应页面 PG2～PG3 由用户确认。

详细的公共组件接口、响应式规则和页面映射见 `page-top-component-spec.md`。
