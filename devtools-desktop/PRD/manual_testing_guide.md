# DevTools Desktop 优化项手动测试指南

本指南提供了针对 DevTools Desktop 五项核心优化指标的实地手动测试步骤、前置准备及预期结果。

---

## 1. 智能端口冲突诊断与强释 (Smart Port Release)

### 1.1 前置准备
在后台模拟一个占用目标端口（以 `8080` 端口为例）的非关联进程：
```bash
# 在终端中执行以下任一命令以霸占 8080 端口
nc -l 8080
# 或者
python3 -m http.server 8080
```

### 1.2 测试步骤
1. 打开 DevTools Desktop 客户端，进入“**本地运行**”面板。
2. 找到一个配置了使用 `8080` 端口的项目（如果未配置，可在卡片中点击“**配置**”将启动命令附加 `--port 8080` 或在环境里配置该端口）。
3. 点击“**▶ 启动运行**”或直接点击“**快速启动**”。
4. 观察项目卡片的变化。

### 1.3 预期结果
1. 项目卡片在检测到启动阻碍后，状态状态栏由正常的灰色“尚未运行”变更为高对比度的黄色警示框，提示：
   `⚠️ 端口 8080 被 nc (PID: XXXX) 占用`。
2. 右侧操作栏自愈按键联动变化，出现 `⚡ 一键释放并启动` 黄色高亮按钮。
3. **自愈验证**：点击 `⚡ 一键释放并启动` 按钮，后台占用的 `nc` 进程被同步强杀释放；本地服务在极短延迟后自动重新触发启动逻辑并顺利运行成功。

## 2. 终端多标签会话热恢复 (Hot Session Restoration)

### 2.1 测试步骤
1. 进入“**快捷命令**”页面。
2. 连续点击 `＋` 按钮新建 3 个终端标签页（分别显示 Terminal 1, Terminal 2, Terminal 3）。
3. 切换至 **Terminal 2**，在 Shell 中输入 `cd /tmp` 并敲击回车。
4. 切换至 **Terminal 3**，输入 `cd ~`（或进入任意特定目录）并敲击回车。
5. 模拟应用非正常退出或热更新重启：
   * 在控制台或任务管理器里直接强杀（Kill）当前的 DevTools 客户端进程。
   * 或者直接关闭窗口重新打开软件。
6. 再次打开软件，切换至“**快捷命令**”页面。

### 2.2 预期结果
1. 页面加载时自动请求 SQLite API，无需用户重新创建，**自动还原出 3 个终端 Tab** 且顺序及命名保持一致。
2. 切换到 **Terminal 2**，输入 `pwd` 检查当前工作路径，预期其直接处于 `/tmp` 目录下。
3. 切换到 **Terminal 3**，输入 `pwd`，预期其处于当前系统的家目录下。

## 3. WebGL 硬件加速与降级自愈 (WebGL Terminal)

### 3.1 测试步骤
1. 切换至“**快捷命令**”终端页面，新建一个终端 Tab。
2. 开启浏览器的开发者控制台（DevTools）以查阅运行日志。
3. 在终端中执行高吞吐量的命令以模拟海量日志输出：
   ```bash
   # 例如在 macOS 下递归检索根目录文件以爆破日志
   find / -name "*.js"
   ```
4. 观察控制台输出以及文字的高分辨率渲染平滑度。

### 3.2 预期结果
1. 开发者控制台中能捕获到 `[WebGL Terminal] Enabled hardware acceleration successfully...` 的日志，表明终端渲染器已成功升级到 GPU 加速层。
2. 即使在高速、大吞吐的日志滚动下，终端渲染依然丝滑、文字清晰，无任何帧率断断续续的情况。
3. **降级自愈测试**：通过人工模拟（如显卡切换、休眠或人工在代码中抛出 context lost 信号），WebGL context 发生丢失：
   * **预期结果**：控制台输出 `[WebGL Terminal] WebGL context lost, disposing addon and falling back...`。终端能自动卸载 WebGL 并平滑退化到普通的 Canvas 2D 渲染器，不中断用户的输入操作，也不引发客户端崩溃。

## 4. 编译与服务日志分级智能染色 (Log Colorizer)

### 4.1 测试步骤
1. 进入“**本地运行**”面板。
2. 启动一个会发生编译报错或缺失依赖的项目（也可以故意在配置中填入错误的启动指令以产生 `Command not found` 或 `module not found` 错误）。
3. 点击卡片上的“**查看日志**”按钮以打开日志弹窗。
4. 查看流出的文本行。

### 4.2 预期结果
常规 stdout 输出原本都是以 `'info'` 类型传给前台，但染色过滤器会对其进行二级提炼：
1. 若日志行中包含 `Error:`, `Failed`, `Exception`, `SyntaxError` 等错误标记，该行会被整行渲染为**淡红色底色高亮**（`log-error`）。
2. 若日志行中包含 `Warning:`, `warn`, `Deprecated` 等警告，该行被整行染成**淡黄色底色高亮**（`log-warn`）。
3. 若包含 `Compiled successfully` 或 `Listening at` 等就绪文本，该行文本呈现**前景色亮绿色高亮**（`log-success`）。

## 5. 报错堆栈一键源码溯源 (Click to Open Editor)

### 5.1 测试步骤
1. 打开刚才产生编译报错的项目日志弹窗（确保日志中包含如 `src/App.jsx:45:10` 等符合路径规则的报错堆栈）。
2. 移动鼠标到该堆栈路径字符上方。
3. 点击该超链接。

### 5.2 预期结果
1. 报错堆栈中的文件名及行号（如 `src/App.jsx:45`）已自动被转换为**带下划线的数据超链接**（悬停时有不透明度渐变反馈）。
2. 点击链接，前端向后端发送 `open-editor` 异步请求，系统自动拉起配置的 **VS Code** 窗口，并**直接将光标跳转到 `src/App.jsx` 的第 45 行**。
3. **降级兜底测试**：如果测试机没有将 `code` 添加至环境变量，后端在首选尝试报错后将自动降级执行 `open` 指令：
   * **预期结果**：使用系统关联的默认编辑器（如 Xcode、Sublime 或内置文本编辑）自动打开对应的源文件。
